# VA 开户费全额免收与待审批申请减免设计

日期：2026-09-11

状态：用户已确认开发；功能已在 `codex/va-opening-fee-waiver` 实施，隔离本地 PostgreSQL 迁移及并发测试通过；未执行生产迁移或部署。

## 1. 范围

在现有银行固定 USD 开户费基础上，支持内部人员免收、特殊普通客户免收，以及已提交申请的单笔全额减免。V1 仅全额免收，不包含部分折扣、已扣费用退款、自动批量减免或恢复已减免费用。

客户身份与收费待遇分离：普通客户可以获得特殊减免，但身份、登录权限、KYC 和账户审批要求不变。内部人员必须是后台创建且由有权限管理员明确标记的客户，不能仅根据后台创建、邮箱域名或管理员代提交推定。

## 2. 客户级待遇

| 客户身份/情况 | 新申请待遇 | 计费依据 |
| --- | --- | --- |
| 普通客户，无特殊免收 | 银行标准收费 | 标准收费 |
| 普通客户，有特殊免收 | 全额免收 | 特殊客户减免 |
| 已确认内部人员 | 自动全额免收 | 内部人员减免 |
| 银行本身明确配置为零 | 免费，减免金额为零 | 银行免费 |

- V1 覆盖所有银行后续新提交的 VA 申请，持续至管理员撤销。
- 银行停用、币种不支持、费用未配置、客户未激活等现有校验继续生效。
- 免费申请不要求具备足够的手续费余额，不冻结钱包，也不创建零金额 Operation 或凭证。
- 客户待遇和身份修改分别控制权限，必须填写原因，保存操作人、时间、修改前后值及版本。
- 内部身份取消后默认恢复标准收费；继续享受特殊免收须显式设置，不恢复隐藏的旧优惠。
- 不自动推定已有客户身份，不自动修改历史申请。

## 3. 已提交申请的单笔全额减免

| 申请状态 | 减免行为 |
| --- | --- |
| SUBMITTED 且关联手续费仍有效冻结 | 允许全额减免并释放冻结，申请继续待审批 |
| SUBMITTED，原本免费或已减免 | 不重复处理，展示既有计费依据 |
| APPROVED，手续费已扣除 | 不允许此操作；退款不在本期范围 |
| REJECTED / CANCELLED | 不需要减免；保留历史与原释放记录 |

管理员在 VA 详情点击“全额减免”，核对客户、银行、申请编号、金额并填写原因。内部人员记为“内部人员减免”，普通客户记为“特殊客户减免”。本次操作仅作用于该申请，不自动改变客户级待遇。

确认文案示例：

> 确认后将释放已冻结的 USD 100.00。本申请保持待审批，批准时不再收取开户手续费。本次操作仅适用于当前申请。

在同一 Render PostgreSQL 串行化事务中：

1. 验证租户、操作权限、申请待审批状态，以及关联 Operation 的类型、状态、金额和钱包归属。
2. 将该笔费用从 USD 钱包冻结余额释放回可用余额；校验失败时整体回滚，不补加余额。
3. 将原 VA_OPENING_FEE Operation 从 SUBMITTED 改为 CANCELLED，保存明确业务原因“开户费全额减免”。
4. 保存不可变减免记录及当前应收为零的结果，保留原费用流水关联；申请仍为 SUBMITTED。

该释放不产生会计凭证或平台收入。批准、拒绝、客户取消路径必须识别费用已减免，避免再次扣除或释放。

## 4. 费用快照与记录

- 提交时保存银行标准费用和版本、提交时应收金额、减免金额、计费依据及客户待遇版本。
- 对提交后减免，保留提交时金额快照；追加单笔减免依据、金额、操作人、时间、原因，不将原始金额覆盖成零。
- 当前应收由原快照与有效减免记录确定。客户后续身份或待遇变化不得改写既有申请计费结果。
- 费用 Operation 取消与 VA 申请取消必须在页面及 API 中明确区分。
- 示例历史：应收 USD 100 → 冻结 USD 100 → 全额减免 USD 100 → 释放 USD 100 → 当前应收 USD 0。
- 内部减免、特殊减免、银行免费分别筛选统计；一笔申请只计一次实际减免，不能同时计入两类。银行免费不计入减免金额。
- 平台收入继续以实际入账凭证为准；减免记录仅解释未收费用，不生成虚构收入、退款或冲正。

## 5. 页面与权限

- 客户新增/详情：分开展示客户身份与 VA 开户费待遇。普通客户可选标准收费或特殊全额免收；内部人员展示自动免收。
- 修改待遇时，提示待审批收费申请数量及冻结总额；保存后提供查看入口，管理员逐笔处理，不默认批量释放。
- VA 申请详情：展示原费用、当前应收、费用状态和减免依据；满足条件且有权限时展示“全额减免”。
- 客户端新申请显示服务端计算的有效费用；提交后减免显示“开户手续费已减免，冻结的 USD … 已释放”。
- 免费申请的取消提示不得宣称释放了实际不存在的冻结费用。
- 客户端仅返回必要费用和状态，不返回内部身份、操作人、内部原因、租户键或平台账户信息。
- 复用现有 Dialog、表单提示和反馈组件，不使用原生 alert / confirm。

## 6. 开发边界

- 内部标识与收费待遇各自只有一个权威数据来源；现有 Go 客户资料和 Core 客户模型的同步不得覆盖设置或引入过期判断。
- 客户级设置变更与减免审计原子提交。资格读取、版本校验、费用决定与申请创建处于一致性事务边界内。
- 报价和提交共用服务端计费规则；客户端不可指定或伪造内部身份与减免资格。
- 银行规则或客户待遇变化后须重新确认；相同幂等请求重试返回原申请及原计费结果。
- 单笔减免只能经专用、租户隔离且受权限保护的 VA 流程处理；不能从通用 Operation 接口绕过。
- 并发减免、批准、拒绝、取消以数据库状态约束决定结果。后到操作读取已完成状态并返回明确结果，不重复释放或扣费。
- 复用现有资金账本，不新增另一套手续费账本；字段、端点和审计落点在实施前结合代码确定。
- 历史数据保留原计费语义，不回填推测的内部身份、特殊优惠或减免记录。

## 7. 验收要点

- 普通客户标准收费与原冻结、扣除、释放流程不变。
- 内部人员与特殊普通客户均可免费提交，零手续费余额不阻断；后台两类准确区分。
- 原本收费的待审批申请减免后原快照不变，冻结恰好释放一次，申请状态不变，原 Operation 取消且有减免原因。
- 减免后批准不扣费，拒绝或取消不重复释放，不产生凭证；重复提交/点击无重复资金变动。
- 已批准、已拒绝、已取消申请不能通过此操作改变资金；异常冻结记录使事务整体失败。
- 身份/待遇修改不追溯既有申请；报价变化重新确认，取消内部身份不意外恢复旧优惠。
- 客户伪造减免、无权限管理员操作、跨租户访问均失败；客户端不泄露内部审计信息。
- 并发操作结果保持一致，钱包、申请、Operation、减免记录相互匹配。
